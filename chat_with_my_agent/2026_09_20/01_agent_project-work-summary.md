# 工作報告：08-14 ～ 09-20

## 報告總覽（30 秒版本）

這一個多月做了三件事：

1. **替轉寫選定新引擎**——評估過 TargetDiarization 後，一天內改拍板 MOSS-Transcribe-Diarize（0.9B），用 vLLM 部署驗證通過，並做成可操作的測試介面。
2. **跑通一條端到端的自動剪片管線**——從 94 分鐘的 YouTube 影片，自動完成轉寫、逐字時間對齊、關鍵詞定位、剪片與編碼，產出 423 片肯定詞片段與 14 片片尾身份片段，全部驗證通過。
3. **超長音訊管線首跑**——為解決「等分盲切」與「跨段說話人無法對上」兩個舊缺陷，設計並執行四階段新管線，在 2 小時 10 分的直播檔上全程跑通（10 位全域語者），並用對照組實驗確認剩餘品質問題來自資料而非演算法。

目前停在：直播檔的說話人分離品質需人工抽聽裁決，裁決後決定調參重跑或人工對映。下一步是把整條管線打包成可呼叫的 API 服務（上傳音訊 → 查詢狀態 → 下載轉錄稿），詳見〈下一步〉一節。

## 背景：這個專案在做什麼

一句話：把長影片或長錄音丟進系統，自動產出**結構化的文字記錄**——不只逐字稿，還包括每句話是誰說的、說話當下畫面裡有什麼、以及整體內容的總結。

八月之前已完成的地基（本報告不展開，僅供定位）：

- **推論核心**：vLLM + Gemma-4-12B 量化模型，文字／圖片／影片／音訊四模態全通，並確立「先自由思考、再強制結構化輸出」的兩階段輸出策略。
- **架構**：把 1277 行的單體 prototype 重寫為 v0.1.1 模組化架構（profiles / modules / framework / workflow），27 項三層測試全過。
- **語音服務**：SAM-Audio 聲音分離、QuarkAudio 目標說話人提取、voicetag 聲紋識別各自服務化，加上 Breeze-ASR 轉錄，整合成 Gradio WebUI——「誰、在何時、說了什麼」的 JSON 已能端到端輸出。

進入 08-14 時，缺的是一塊：**正式的 STT（語音轉文字）引擎**。模組都還是空殼。

## 任務一：轉寫引擎選型——一天內推翻前一天的結論（08-14、08-18）

### 經過

**08-14**，因為 STT 模組還是空殼，認真評估了外部專案 TargetDiarization：派四個 sub-agent 從架構、相容性、音訊處理、工程實務四個維度做完整對比。結論是它像一座「功能完整的音訊處理工廠」（降噪、人聲分離、標點還原、多引擎 ASR、雙層說話人日誌一應俱全），值得整合，並規劃了四階段整合路線圖。

**08-18**，研究到 OpenMOSS 的 MOSS-Transcribe-Diarize 後，**親手推翻了這個結論**。這是一個 0.9B 的小型音訊語言模型，單次推理就能同時完成轉寫、說話人日誌和起訖時間戳——相比之下 TargetDiarization 的多階段工廠顯得笨重。當場拍板改用 MOSS-TD，前者降級為參考實作。

決定容易，驗證不易：

- 先試 sgl-omni 伺服器，連續三輪都在第一個推理請求時崩潰，確認無救後改用 vLLM 部署——跑通後才發現原來失敗根因只是沒裝 soundfile。
- 部署打通後資料漂亮：兩分鐘的會議音訊，四位說話人全數分出且與實際吻合，處理延遲只有 7.5～10 秒（RTF 0.07~0.08）。

### 踩坑與對策（之後所有實驗都受益）

| 踩到的坑 | 對策 |
|---|---|
| 不同輸出格式的併發請求會**回應錯位**（收到別的請求的錯誤） | 生產管線序列化（`threading.Lock`） |
| 官方 `hotwords` 欄位會讓時間戳消失、品質變差 | 改用 `prompt` 帶熱詞——但發現它會降低 diarization 粒度（4 人變 3 人），熱詞與分群不可兼得 |
| 模型不跟隨繁體中文指令 | 管線後處理用 OpenCC s2t 轉繁體 |
| 起訖時間戳嵌在文字的 `[start][Sxx]text[end]` 標記裡 | 寫 regex 解析器抽出 |

當天就把這些包裝成一支可操作的測試介面（`webuis/moss-playground.py`），端到端實測通過。

### 這一段的啟示

08-14 的四維度研究沒有白費——正是它建立的判斷框架，讓隔天能一眼看出 MOSS-TD 的架構優勢。研究結論要敢於被新證據推翻。

## 任務二：端到端自動剪片實驗（08-26 ～ 09-01）

### 目標

從一支 94 分鐘的 YouTube 影片（N9boWvU-KkA）中，自動剪出所有「肯定回應」片段——來賓說「對」「沒錯」「OK」這類短語的瞬間，供後續剪輯使用。

### 管線全貌

```
下載影片 → 轉寫（963 段）→ 轉繁體 → 盤點肯定詞 → 強制對齊（逐字時間點）
  → 修時間戳 → 定位關鍵詞 → 剪片（423 片）→ 編碼交付
```

### 各步關鍵結果

- **下載**：yt-dlp 下 AV1 1080p + Opus 兩路分流，自動合流失敗，改 `ffmpeg -c copy` 封裝 MKV 一次成功（94 分 27 秒、1.05GB）。
- **轉寫**：94 分鐘音訊等分 4 段序列送 MOSS ASR，963 segments 全成功，offset 合併成單一逐字稿。
- **強制對齊（本實驗最難的一步）**：選用 Qwen3-ForcedAligner-0.6B，走 vLLM 的 `/pooling` 端點做逐字時間對齊。伺服器預設 chat template 會丟掉文字部分，加 `--trust-request-chat-template` 重啟才跑通。對齊品質用四種獨立方式交叉驗證（silencedetect、MOSS ASR 比對、逐幀目測）全數吻合。附帶發現：音訊頭尾留空會讓模型把預測「均勻攤開」，送對齊的片段 padding 要小（約 100~200ms）。
- **剪片**：`edit_video.py` 支援 dry-run / 限量 / 全量 / 驗證四模式。**全量 423 片、0 失敗、47.3 秒跑完**，驗證全過。
- **片尾身份切片**（09-01）：另一個需求——剪出片尾用的日期、頻道名、書名、來賓介紹。一天迭代三版，最終版 `cut_intro_sentences.py` 做到**逐句各剪一片**：短句「對」全文出現多次，用時間順序遊標消歧（按清單順序、從上一句之後往後找，找不到就整體報錯、絕不輸出半成品）。14/14 成功，時間偏差 ≤0.06 秒。

### 失敗與教訓（每次失敗都轉成了知識）

| 失敗 | 根因 | 教訓 |
|---|---|---|
| 逐字字幕中段全部堆疊 | 抄對齊流程時跳過了官方 `fix_timestamp` 後處理 | 動官方演算法前先搞懂每一環的用途；補上後反轉區間 11→0 |
| 無損剪片切點偏移 3.63 秒 | 影片 GOP 固定 6 秒，切點被拉回前一關鍵幀 | 原估「偏差 0.1~0.5 秒」不成立；無損複製對長 GOP 影片不可行 → 改逐片重編碼 |
| GPU 硬體 AV1 編碼（NVENC）一開並行就 OOM | 同臺 GPU 的 sglang 推理服務佔掉九成視訊記憶體 | 硬體編碼路線確定死亡，退回 CPU |
| AV1 編碼的 MP4 在 DaVinci Resolve 裡是黑幀 | 容器格式相容性問題 | 同內容的 MKV 正常——**容器格式直接影響下游軟體**；最終用 CPU libsvtav1 + MKV 全量重產 423 片（24 分鐘、驗證全過） |
| 輸出資料夾被外部程式持續刪檔 | 來源未明 | 未解之謎，改用新輸出目錄繞開 |

## 任務三：超長音訊管線首跑與說話人統一（09-16 ～ 09-20）

### 為什麼要重做

舊管線有兩個已知缺陷：

1. **等分盲切**——長音訊按固定長度切，句子會被攔腰切斷。
2. **跨段說話人無法對上**——第 1 段的「S01」和第 7 段的「S03」可能根本是同一個人，但系統不知道。

### 四階段設計

1. **迭代切分轉寫**：不盲切，轉寫到逐字稿尾端後回掃句界（完整句）定切點，迴圈到片尾。
2. **段內分群抽音色**：每一段內做說話人分群，每個語者取一個音色代表（centroid）。
3. **全域說話人統一**：所有段的音色放進全域相似度矩陣，用帶約束的 union-find 合併，頒布全域唯一的說話人標籤。
4. **組裝輸出**：時間 offset 平移 + 加上 `speaker_global` 欄位。

### 執行

- 執行前先在**舊資料**上做煙霧測試——事後證明極有價值：發現原定相似度閾值 τ=0.75 過嚴（把八組全部誤判為歧義），上調到 0.90 並改為事後審查，避免了在正式資料上白跑。
- 執行中 ASR 伺服器連續四次啟動失敗（同臺 GPU 上的 176B 模型佔走 97GB 記憶體 → CUDA OOM），依「偏離即停」規則停下等人裁決，而不是硬闖。裁決後以 sglang-omni 啟動，全程跑完。
- **結果**：2 小時 10 分直播檔，7 段、4096 句、零重試、零盲切（約 29 分鐘）；**10 位全域語者 + 2 位無法定案者**（各僅一段、不足 1 秒，取不到可信音色）。

### 發現問題：分離餘裕是負的

品質檢驗亮紅燈：**分離餘裕 −0.103**。有兩個音色相似度高達 0.9494 的語者，被段內唯一性約束硬生生拆成兩個全域標籤——疑似段內 diarization 把同一人拆開了，這與「段內標籤可信」的設計前提衝突。

### 對照組實驗：是演算法的錯，還是資料的錯？（09-20）

為了回答這個問題，做了一個乾淨對照：拿一段 1 小時 53 分的正式會議錄音（乾淨音訊）走同一條管線，並新寫了 `tau_sweep.py` 把「用耳朵調閾值」升級成自動化掃描——音色編碼一次，對 τ 網格（0.10~0.70）逐值試分群，自動選出最寬的穩定平臺期中心當自適應閾值。

| | 乾淨會議 | 髒直播（Ek7） |
|---|---|---|
| 全域語者 | 6 群 + 0 未定 | 8 群 + 2 未定 |
| 投票一致率 | **0.961** | 0.7529 |
| 自適應 τ | 0.225 | 0.2 |
| τ≥0.50 的穩定訊號 | 有（第二平臺 0.55~0.65） | 全無（37 叢集全開） |

**結論**：一邊倒的對比支援「直播檔的難度主要來自資料汙染」（背景音樂、酒後嗓音變化把音色空間擠在一起），演算法本身站得住。另外，τ 自適應幾乎免費——音色編碼本來就要算，多次分群只需秒級。

## 學到的事

- **研究結論要敢被推翻**：TargetDiarization 的深度研究沒白費，正是它讓 MOSS-TD 的優勢一眼可辨。
- **官方後處理不能跳過**：fix_timestamp 的教訓——整合第三方工具前，先搞懂每一環存在的理由。
- **容器格式影響下游相容性**：MKV vs MP4 不是「能不能播」的問題，是 DaVinci 黑幀的問題。
- **煙霧測試要在舊資料上做**：在便宜的資料上調參，比在正式資料上反覆試錯便宜得多。
- **識別品質與參考音訊長度正相關**：0.34 秒的參考音訊幾乎等於沒有。
- **偏離即停**：GPU 被 176B 模型佔滿時停下等人裁決，比硬闖省時間。

## 下一步：管線服務化（API Endpoint）

目前管線仍以本機指令碼與 WebUI 操作為主，一次只能服務一個使用者。接下來的規劃是把它打包成**可呼叫的 API 服務**（FastAPI 或 MCP-Server 形式），預期提供三個基本能力：

1. **上傳音訊**：使用者或外部 Agent 直接把音訊送進服務，不再依賴本機檔案路徑。
2. **查詢處理狀態**：長音訊處理以分鐘計（2h10m 的檔案全程約半小時），必須走非同步任務＋狀態查詢的模式，而非同步等待回應。
3. **下載完整轉錄稿**：處理完成後取回結構化結果（逐字稿＋說話人標籤＋時間戳）。

服務化會牽動幾個既有設計的升級：任務佇列與狀態機需要新設計；08-18 發現的「併發回應錯位」在多使用者場景下會更關鍵，目前的序列鎖要升級為正式的任務管理；GPU 容量規劃也要面對多請求共存的現實。

另外，關於處理成果的**歸檔與組織**——會議經驗、對話中的知識、檔案等不同來源的資料，如何融合存放並讓 AI 日後能有效取用——還在架構發想階段，考量範圍較大，需要一段時間醞釀；本次僅說明方向，尚無具體設計。
